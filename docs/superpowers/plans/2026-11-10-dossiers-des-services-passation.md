# Les dossiers des services — passation entre conversations

Le plan (`2026-11-10-dossiers-des-services.md`) est réalisé en cinq phases, chacune dans sa propre conversation Claude, avec le modèle indiqué. C'est l'utilisateur qui crée chaque conversation et choisit le modèle. Une conversation enchaîne toutes les tâches de sa phase sans s'arrêter, puis s'arrête et annonce la suivante. Même méthode que `2026-11-10-bureau-vivant-passation.md`.

## Où on en est

Tenir cette section à jour à la fin de chaque phase (dernière action avant le dernier push).

Notes laissées par les phases précédentes (écarts au plan, choix faits, points à surveiller) :

**Phase A (tâches 1 à 5, faite).**

- *Écart — la direction n'est pas dans `services`.* Le résultat de `cout.facturation` (et de `GET /api/facturation`) range le chef et les usages sans service dans une clé **`direction` au même niveau que `services`** (même forme : `{total, taches, modeles, usages}`), et non dans `services["direction"]` comme l'écrit le plan : un projet peut avoir un service d'identifiant `direction`, les deux se seraient mélangés sans le dire.
- *Forme exacte de `GET /api/facturation?periode=…`* (pour la phase B) : `{disponible: true, periode, total, gestion, sans_prix: [{modele, tokens, usages}], services: {id: {total, taches: {id: {total, etapes: {nom: euros}}}, modeles: {nom: euros}, usages: [...]}}, direction: {même forme}, sources: [{id, genre, service, tache, texte}], prix_du, avertissement, maj, message}` ; ou `{disponible: false}` (relevé en version < 3, relevé en erreur, ou aucun usage ni dans le relevé ni dans l'historique). Dans `taches` et `etapes`, la clé **`""`** veut dire « hors tâche » / « sans étape » (aucun identifiant réel n'est vide). Un usage de `usages` : `{id, tache, agent, modele, etape, t, tokens: {entree, sortie, cache_lecture, cache_ecriture}, cout (euros ou null si prix inconnu), prix_du, ancien}`. `genre` d'une source : `tache_chere`, `modele_trop_fort`, `allers_retours` (une source par tâche) ; identifiant `source:<service>:<genre>:<tache>`, à recalculer par `cout.id_source`. `message` vaut null quand les prix sont à jour, sinon le texte à montrer (« Prix du …, mise à jour impossible : … », prix automatiques coupés, valeur absurde gardée). `gestion` vaut toujours 0 (le bureau ne consomme aucun token). `cout.euros_en_clair(x)` donne « ≈ 4,20 € » (le serveur l'utilise dans les textes des sources ; la page doit faire de même avec « ≈ »).
- *Écart — la source de prix s'injecte à la construction* : `serveur.creer(chemin, port=None, ouvrir=None)` et `Bureau(adresse, chemin, ouvrir=None)` ; `Bureau.ouvrir` existe toujours. Raison : le fil des prix démarre dans le constructeur, donc un test qui remplacerait `ouvrir` après coup arriverait trop tard (les tests serveur passent une `SourceSimulee`). `Bureau._fil_prix` vaut `None` si `prix_automatiques` est faux **ou si les réglages sont illisibles** (aucune requête dans le doute). Remettre `prix_automatiques` à vrai demande un redémarrage ; le mettre à faux est respecté dès l'heure suivante.
- *État* : `etat["dossier"] = {facturation, kpi, connaissances}`. Pour l'instant `kpi` = un service du relevé v3 a une liste `kpi`, `connaissances` = une liste `challenges` ou un titulaire avec une liste `connaissances` ; les phases C et D valident ces champs et peuvent affiner ces deux règles dans `etat.dossier(r)`. `facturation` est aussi vrai quand l'historique contient des usages (le serveur l'ajoute).
- *Relevé, petits choix* : un usage peut avoir `agent: null` (rangé en direction) ; la clé `chef` ajoutée par la normalisation est un agent connu quand le projet ne déclare pas de chef ; `t` doit être une date ISO lisible ; `cache_lecture`/`cache_ecriture` valent 0 par défaut après normalisation.
- *Prix, choix de réalisation* : après la première lecture, la table ne garde que les prix qui changent ; une valeur absurde est rejetée **modèle par modèle** (le reste de la liste est pris) ; un modèle neuf à 0 $ dans la liste (modèles locaux) est ignoré sans bruit → « prix inconnu » ; un prix de cache absent compte au prix d'entrée ; une correction à la main sans `date` lisible est ignorée (elle bougerait le passé).
- *À surveiller — certificat de la BCE sous Windows.* Sur la machine de l'utilisateur, Python ne peut pas vérifier `www.ecb.europa.eu` (autorité Sectigo Public Server Authentication Root E46, que Windows n'installe qu'à la première visite par un programme Windows). Le bureau le dit en clair dans `message` ; mais **sans aucun taux enregistré, tous les prix restent « inconnus »**. La phase E doit l'écrire dans `docs/installation.md` (ouvrir une fois l'adresse du taux dans Edge). La liste de LiteLLM pèse 3,4 Mo (limite 5 Mo) : à surveiller.
- *À surveiller — une erreur de test vue une fois.* En fin de phase A, un passage complet de `unittest` a donné « FAILED (errors=1) » sans que le test fautif ait été noté, puis dix passages de suite ont été verts. Cause probable corrigée : le fil des prix pouvait encore écrire dans le dossier temporaire d'un test après la fermeture du serveur (`server_close` attend maintenant ce fil). Si l'erreur revient, noter le nom du test.
- *Commits* : le plan écrit « Co-Authored-By: Claude Sonnet 5.5 » ; chaque phase signe avec son propre modèle, comme le dit ce fichier.

**Phase B (tâche 6, faite).**

- *Écart — seuls deux onglets existent.* `dossier.js` exporte `ongletsDisponibles(etat)` : Tâches (toujours) et Facturation (si `etat.dossier.facturation`). La phase C ajoutera Connaissances et la phase D KPI dans cette fonction et dans `dessiner()` (une branche par onglet) ; un onglet sans module n'est pas montré plutôt que vide. `contenuDossier(ctx, conteneur, service, onglet?)` garde onglet et période dans une variable de module (`choix`), et dessine aussi la liste des agents sous les onglets.
- *Écart — le panneau « service » ne reçoit plus la phrase ni la liste d'agents de `panneaux.js`* : tout vient de `contenuDossier`. La signature du panneau inclut `etat.dossier` et les tâches actives, pour redessiner quand elles changent. `ctx.ouvrirTache(id)` ouvre une tâche depuis le dossier.
- *Facturation côté page* : `facturation.js` exporte `chargerFacturation(periode)` (fetch, 15 s, erreur lisible), `serviceFacture`, `lignesTaches`, `lignesModeles`, `dessinerFacturation`. La clé `""` devient « Hors tâche » / « Sans étape ». Le bouton « Challenger » des sources est désactivé (« Bientôt disponible ») : la phase C doit l'activer (c'est dans `dessinerFacturation`). L'onglet Tâches affiche le coût de chaque tâche en cours (même appel, silencieux en cas d'échec). La direction (`donnees.direction`) n'est pas montrée : elle n'a pas de dossier.
- *Texte* : `texte.js` gagne `euros`, `tokens`, `libellePeriode`, `PERIODES`, `PERIODE_DEFAUT`. Le sélecteur de période est masqué si le relevé ne fournit pas de facturation.
- *Vérifié au navigateur* sur une copie de la démo en version 3 (usage inventé, modèle hostile `<img onerror>`, prix à la main, `prix_automatiques: false`) : onglets, période qui recharge, prix inconnu visible, texte hostile affiché tel quel, console vide. Pas de capture d'écran gardée (la capture du dossier est à refaire en phase E).

**Phase C (tâches 7 à 9, faite).**

- *Relevé* : par titulaire `connaissances` (`{id, texte, date?, origine?, appris_de?: [{agent, tache?, retour?}]}`, `agent` = titulaire connu ou le chef ajouté) et `challenges` à la racine (`solutions` facultatif → `[]`). Identifiants uniques **par genre** dans tout le relevé (connaissances entre elles, challenges entre eux, solutions de tous les challenges entre elles) ; une leçon peut partager l'id d'une connaissance (la connaissance l'emporte). `tache` d'`appris_de` n'est pas vérifiée contre les tâches (une tâche finie peut quitter le relevé). Une liste absente **reste absente** après normalisation (elle masque l'onglet).
- *État* : `agent["connaissances"]` = connaissances + leçons **validées** du titulaire, chacune `{id, texte, date, origine, appris_de, partagee, lecon}` ; chaque `appris_de` reçoit `prenom`, `service`, `titre`. **Écart** : `etat["savoir"]` = `[{agent, prenom, service, present, connaissances}]` — tous les agents présents, plus les **partis qui ont des connaissances** (sinon leur savoir disparaîtrait du dossier) ; l'onglet Connaissances lit `savoir`, pas `agents`. `etat["challenges"]` = liste du relevé. `dossier.connaissances` est aussi vrai en v3 si un titulaire a une leçon validée. `probleme_revenu` n'existe pas encore : la tâche 10 l'ajoute sur les connaissances de `savoir` (c'est le même objet que dans `agent["connaissances"]`), la page l'affiche déjà (marque « problème revenu »).
- *Demandes* : `verifier(demande, r, cibles_calculees)` ; `cibles_calculees` est un **dict id → constat** (un ensemble marche aussi). **Écart** : `Bureau.cibles_calculees(r, regl)` fournit **déjà** les sources (`cout.facturation`, union des trois périodes), sinon le bouton « Challenger » de la facturation aurait toujours répondu 400 ; la tâche 10 n'a qu'à y ajouter les KPI calculés. Le bureau remplace `texte` par le constat calculé (+ le texte de l'utilisateur à la suite). Calcul fait seulement pour une cible `kpi` ou `source`. **Choix** : une cible KPI a l'id `kpi:<service>:<id>` **aussi pour les KPI du projet** (les id ne sont uniques que par service) ; la page de la phase D doit fabriquer le même id, et la phase E doit le documenter (le projet reçoit `kpi:dev:defauts`). Toute demande de challenge est refusée sur un relevé v1/v2. Une cible `connaissance` vise une connaissance ou une leçon validée.
- *Double clic* : la page grise le bouton avant l'envoi et garde « Demande envoyée » (mémoire de session) tant que le relevé ne montre pas le challenge ; le serveur vérifie **dans le verrou des demandes contre le relevé relu** (`etat(bloquant=True)`) et refuse 120 s un second challenge sur une cible déjà envoyée (`GARDE_CHALLENGE_S`). `do_POST /api/demande` rend 500 en JSON au lieu de couper la connexion.
- *Page* : `connaissances.js` (`contenuConnaissances`, purs `dansLaPeriode`, `agentsSansApport`, `provenances`), `challenge.js` (`contenuChallenge`, `enAttenteCible`, `marquerEnvoye`), `actions.js` (`demandeChallenge`, `demandeSolution`, `demandesVerdicts`, `challengeDe`, `resumeEnvoi`). Le volet s'ouvre dans la zone du dossier par `ctx.challenger(cible, constat, taches)` (fourni par `contenuDossier`, gardé dans `choix.challenge`) ; **la phase D l'utilise pour les KPI** avec `{type: "kpi", id: "kpi:<service>:<id>"}`. Le sélecteur de période se montre aussi pour l'onglet Connaissances. `dateFr("2026-10-01")` rend « 1 oct. » (plus d'heure inventée).
- *Vérifié au navigateur* sur une copie v3 de la démo : onglet Connaissances (partagée, appris d'un autre service, agent sans apport), challenge existant (solutions du Directeur et du service, deux validées l'une après l'autre), nouveau challenge avec double clic (une seule demande), challenge d'une source (constat écrit par le bureau), textes hostiles affichés tels quels, console vide.
- *Mineurs laissés (relecture)* : « Demande envoyée » de « Ma solution » se lève dès que le nombre de solutions change (même si c'est le Directeur qui en ajoute une) ; le résumé des verdicts reste affiché ; `dansLaPeriode` lit une date sans heure en UTC (rate « aujourd'hui » à l'ouest d'UTC) ; le constat envoyé pour une source est celui de la première période où elle existe ; un agent parti avec des connaissances reçoit une fiche dans `equipe.json`, un agent parti sans connaissance cité dans `appris_de` garde sa clé ; `_challenges_envoyes` n'est jamais purgé ; pas de garde serveur contre une solution envoyée deux fois après rechargement de la page.
- *À surveiller* : l'erreur intermittente de `unittest` est revenue **une fois** (« FAILED (errors=1) », 285 tests) sans que le nom soit capturé, puis treize passages verts. Prochaine fois : rediriger la sortie dans un fichier avant de relancer.

**Phase D (tâches 10 et 11, faite).**

- *Relevé* : par service `kpi` `[{id, nom, valeur (nombre fini ou texte), unite?, evolution?, alerte?, texte?, periodes?: {aujourdhui, 7j, 30j}}]` ; `id` unique par service, liste absente = reste absente (comme les connaissances), normalisation : `unite`, `evolution`, `texte`, `periodes` → `null`, `alerte` → `false`. Ignoré en version 1 et 2.
- *`bureau/kpi.py`* : `calcules(r, usages_cout, periode, maintenant)` (quatre KPI par service : `taches_terminees`, `allers_retours`, `duree_tache`, `cout_moyen` ; un chiffre sans donnée est **omis**, jamais montré à 0 — sauf `taches_terminees`, toujours là ; les tâches comptées sont celles du service dont `maj` tombe dans la période ; `duree_tache` et `cout_moyen` sont des textes (« 24 h », « ≈ 3,00 € »)), `tous` (ceux du projet d'abord ; **le KPI du projet l'emporte** sur un calculé de même id), `constats` (id `kpi:<service>:<id>` → texte écrit par le bureau, seulement pour les calculés), `cible_kpi`, `HistoriqueAlertes`, `suivre_alertes`, `probleme_revenu`. Un KPI calculé a `calcule: true` et `periodes: {<période demandée>: valeur}` ; un KPI du projet `calcule: false`.
- *Alertes* : `alertes-historique.jsonl` (à côté des réglages) garde un événement par **changement d'état** ; une alerte qui cesse puis revient reçoit une **nouvelle** date de première alerte. Un KPI vu pour la première fois déjà en alerte reçoit la date de cette première lecture (limite : une connaissance plus ancienne sera marquée « revenue » si le bureau est installé après la connaissance et que l'alerte dure).
- *Problème revenu* : `etat.construire(..., alertes=None)` marque `probleme_revenu` (toujours présent, faux par défaut) sur les connaissances de `savoir` et `agents`. Le lien est : `connaissance.origine` == id d'un `challenge` dont la cible est `{type: "kpi", id: "kpi:<service>:<id>"}` ; **la phase E doit le documenter** (l'`origine` doit être l'identifiant du challenge). Une date de connaissance sans heure compte jusqu'à la fin de sa journée locale.
- *Serveur* : `GET /api/kpi?periode=…` (400 sur période inconnue ou répétée ; `{disponible: false}` en version < 3 ou sans onglet) → `{disponible, periode, services: {id: [kpi]}}`. **Écart** : `dossier.kpi` est aussi vrai dès que des usages sont connus (le coût moyen se calcule), pas seulement quand un service a une liste `kpi`. `cibles_calculees` rend les sources **et** les KPI calculés des trois périodes (le constat est celui de la première période où la cible existe) ; il ne dépend plus de la présence d'usages pour les KPI.
- *Page* : `kpi.js` (`valeurKpi`, `etiquettePeriode(kpi, periode?)`, `kpiEnAlerte`, `idCibleKpi`, `nombreFr` purs ; `chargerKpi`, `dessinerKpi`, `contenuKpi`, `rappelAlertes`). Onglet KPI entre Connaissances et Facturation ; le sélecteur de période se montre aussi pour lui ; le rappel des alertes (avec « Challenger » / « Voir le challenge » / « Demande envoyée ») est en haut de l'onglet Tâches et tient la période choisie. Le constat envoyé pour un KPI du projet est son `texte` d'alerte.
- *Vérifié au navigateur* sur une copie v3 de la démo : grille (projet + calculés), alerte et bouton, période qui recharge (30 j), « toutes périodes » sur les KPI sans `periodes`, nom et évolution hostiles (`<img onerror>`, `<script>`) affichés littéralement, aucune balise créée. Pas de capture gardée.
- *Test* : l'erreur intermittente de `unittest` a été attrapée : `test_demandes_successives`, `OSError WinError 145` au nettoyage du dossier temporaire (Windows garde un instant le fichier de la commande d'actions). Ce n'était pas un test faux : `AvecServeur.setUp` utilise maintenant `TemporaryDirectory(ignore_cleanup_errors=True)`. Trois passages complets verts ensuite.
- *Mineurs laissés* : un KPI retiré du relevé garde son alerte « ouverte » dans l'historique ; `allers_retours` compte aussi les tâches non terminées de la période ; pas de capture d'écran de l'onglet (à refaire en phase E avec la démo).

**Phase E (tâche 12 et relecture finale, faite). Le projet 2 est terminé.**

- *Démo* : `exemples/demo/releve.json` est en version 3 (12 usages sur quatre noms de modèle dont « Maison », laissé exprès sans prix ; colonne « Fait » `terminee` ; un KPI en alerte dans Dev avec `periodes`, un KPI « toutes périodes » dans QA ; trois connaissances dont une apprise d'un autre service ; le challenge `c1` sur `kpi:dev:defauts` avec trois solutions). `actions.py` applique les trois demandes : il joue le projet (une solution du Directeur et une du service à l'ouverture, textes fixes), et sur `valider` inscrit la solution dans les `connaissances` des agents concernés (le titulaire de la connaissance contestée, ou les agents du service de la cible) avec `origine` = id du challenge. `reglages.json` porte `alias_modeles` (noms vérifiés dans la liste LiteLLM le 10 novembre 2026). Les usages de la démo sont datés du 9 novembre 2026 : ils sortent des périodes avec le temps (dit dans `docs/installation.md`).
- *Tests* : `tests.copie_demo()` copie la démo **sans** les fichiers que le serveur y écrit (`*.jsonl`, `equipe.json`) ; les tests ne dépendent plus d'une démo lancée sur place. `tests/test_relecture_dossiers.py` porte les cas de la relecture.
- *Relecture indépendante (Fable), puis corrections.* Aucun constat critique. Corrigé, chaque fois avec un test vu en échec d'abord :
  - une valeur absurde rejetée restait signalée une heure au plus : la ligne du jour de `prix-historique.jsonl` porte maintenant une `note`, redite toute la journée et après un redémarrage (`TablePrix.note_du`, `ajouter(..., note)`) ;
  - un usage à prix inconnu faussait sans le dire le coût d'une tâche (onglet Tâches), le KPI « coût moyen » et le constat d'une source : `cout.facturation` donne `sans_prix` **par tâche** (nombre) et **par service** (liste, comme la liste générale) ; la page écrit « ≈ 3,00 € + prix inconnu » (`coutEnClair`), le KPI « (hors prix inconnus) », le constat « Des usages à prix inconnu ne sont pas comptés dans ce coût. » ; une tâche dont aucun usage n'a de prix apparaît avec `total: 0` et `sans_prix > 0` ;
  - le niveau **par discussion**, le total du projet et la part « direction / hors service » n'étaient pas affichés (la conception les demande) : ils sont dans l'onglet Facturation (`lignesDiscussions`, `totalProjet`), avec l'info-bulle de la date du prix sur chaque discussion ;
  - fausse source « modèle trop fort » quand seul le taux de change bougeait d'un jour à l'autre : le niveau d'un modèle est maintenant le même pour tous ses usages de la période ;
  - un challenge devenait inatteignable quand sa cible n'était plus affichée (alerte levée, source sortie de la période) : l'onglet Tâches liste tous les challenges du service (`challengesDuService`) ;
  - historiques non UTF-8 (fichier réenregistré) : la ligne abîmée est ignorée au lieu d'arrêter le bureau ; historique des alertes non inscriptible : la scène reste ; message exact quand les prix automatiques sont coupés ; « 1 tâche » ; date des prix sans double point.
- *Décisions prises à la relecture (non corrigé, assumé).* Changer un `alias_modeles` re-chiffre aussi le passé : un alias est une correction de nom sans date, c'est dit dans la documentation (coût si c'est un mauvais choix : il faudrait dater les alias). La page n'envoie que le verdict `valider` (c'est le plan : une demande par solution cochée) ; `ecarter` est accepté par le bureau et appliqué par la démo, mais aucun bouton ne l'envoie : à décider avec l'utilisateur.
- *Mineurs laissés (relecture finale).* Un prix lu plus tard dans la journée change le coût des usages du même jour ; `prix_automatiques` ne coupe que sur le booléen `false` ; tant que le taux ne peut pas être lu, la liste de prix (3,4 Mo) est retéléchargée chaque heure et une ligne ajoutée ; un vrai changement de prix de plus de ×10 doit être donné à la main ; l'historique des usages n'est jamais purgé et se réécrit en entier (1 s pour 100 000 usages), et `/api/facturation` renvoie tous les usages de la période ; les périodes 7 j et 30 j incluent un usage daté dans le futur, et le jour de prix est lu sans conversion de fuseau ; `kpi:<service>:<id>` est ambigu si un identifiant de service contient « : » et en préfixe un autre ; un coût sous un demi-centime s'affiche « ≈ 0,00 € » dans la page ; une redirection https d'une source de prix est suivie vers un autre hôte https ; « problème revenu » demande que le challenge reste dans le relevé (documenté).
- *Dépôt public* : `git grep` et l'historique relus (par moi et par le relecteur) : aucun nom de projet réel, chemin de machine, courriel, clé ni jeton ; auteur unique à l'adresse « noreply » de GitHub. `exemples/demo/alertes-historique.jsonl` manquait au `.gitignore` : ajouté.

## Ce que chaque conversation doit savoir

**Le cadre**

- Dossier de travail : la racine de ce dépôt. Dépôt GitHub public `maximus49000/MyIAFactory`, branche `main`.
- La conception et le plan sont **validés par l'utilisateur**. Il ne faut ni reposer les questions de cadrage ni refaire un plan : on exécute. La conversation réalise elle-même les tâches de sa phase, dans l'ordre (skill `superpowers:executing-plans`).
- Lire d'abord, en entier : la conception `docs/superpowers/specs/2026-11-10-dossiers-des-services-design.md`, le plan `docs/superpowers/plans/2026-11-10-dossiers-des-services.md`, et ce fichier. Les sections « Global Constraints » et « Review Focus » du plan valent pour toutes les tâches.

**Les règles à ne pas oublier**

- Dépôt public et vide de tout projet : rien de propre à un projet réel, rien de privé.
- Python : `py -3.12`, bibliothèque standard uniquement. Tests : `py -3.12 -m unittest discover -s tests -v` et `node --test "bureau/web/tests/*.test.js"`.
- Aucun test ne sort sur Internet (sources de prix injectées).
- Chaque tâche : test d'abord, le voir échouer, coder, le voir passer. Puis cocher la tâche dans le `README.md`, commit en français terminé par `Co-Authored-By: Claude <modèle de la conversation> <noreply@anthropic.com>`, et `git push`.

**La fin d'une phase**

1. Tous les tests passent (les deux commandes), sortie lue.
2. Mettre à jour « Où on en est » : la phase passe à « fait », et les notes pour la suivante sont écrites.
3. Dernier commit et push.
4. Dire à l'utilisateur, en clair : ce qui a été fait, ce qui n'a pas pu l'être, **quelle est la prochaine phase**, avec quel modèle, et le message à coller pour la lancer (ci-dessous). Puis s'arrêter : ne pas entamer la phase suivante.
